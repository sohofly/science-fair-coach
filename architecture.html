SYSTEM ARCHITECTURE · 系統架構

靜態前端，受控後端，研究資料逐層隔離。

GitHub Pages 負責三個操作介面；Supabase 負責身分、資料、檔案與 Edge Functions；OpenAI 只在需要動態建議時由後端呼叫，API 金鑰不進入瀏覽器。

系統分層

箭頭方向為瀏覽器提出請求；教師可在 RLS 保護下讀寫授權資料，學生的自訂 session 則一律經 Edge Function 驗證。

① 操作介面
學生網站index.html：探索、選題、研究計畫、子題、實驗與心得
教師入口portal.html：Google 登入、班級、歷程、回饋與匯出
總管理者admin.html：教師核准、帳號設定與全站管理
HTTPS / Supabase SDK / JSON API ↓
② 服務與授權
Supabase Auth教師 Google OAuth；登入後仍檢查 teacher_profiles 核准狀態
Edge Functions學生帳號、推薦、實驗檢核、教師帳號操作、管理與清除排程
RLS 與角色檢查教師僅可操作自己的班級；管理 API 另以管理者 session 保護
Service role 僅留在伺服器端 ↓
③ 資料與檔案
PostgreSQL班級、學生、研究主題、事件、計畫、建議、實驗與用量
Storage私有 experiment-files bucket；限制檔案大小與允許類型
排程清除purge-expired 依 active_until / delete_after 執行保存政策
只有伺服器端按需呼叫 ↓
④ 外部服務

OpenAI Responses API動態題目、Web Search、實驗回饋與教師架構草稿
科教館與公開來源作為研究背景線索；作品、日期、科別與網址仍需人工核對

三條關鍵資料流

不同身分使用不同驗證方式，避免讓學生自訂憑證直接存取資料庫。

學生研究流程

  1. 學生帳號登入取得不透明 session token
  2. 瀏覽器以 x-student-token 呼叫 student-api
  3. 函式驗證 token 雜湊、期限與研究擁有權
  4. 更新研究資料並追加 thought_events
  5. 需要 AI 時再由專用函式呼叫模型

教師指導流程

  1. Google OAuth 取得 Supabase JWT
  2. 確認教師已核准且狀態有效
  3. RLS 限制為教師自己的班級與學生
  4. 查看單一學生、單一研究的完整證據鏈
  5. 留言或送出建議，等待學生採用／婉拒

AI 建議流程

  1. 後端先驗證身分、研究與每日用量
  2. 只整理該研究所需的最小脈絡
  3. 以 JSON Schema 限定結構化輸出
  4. 結果作為建議或草稿，不自動代替決策
  5. 記錄來源事件與 AI 用量供追蹤

核心資料模型

資料的主幹是「班級 → 學生 → 研究主題」。所有研究內容都帶 research_id，因此新增主題不會覆蓋舊歷程。

班級classes

屬於一位教師；提供加入碼。

學生students / student_sessions

匿名代號、登入帳號、密碼雜湊與保留期限。

研究主題（資料主幹）research_projects

一位學生可有多個研究；保存題目、條件與目前選擇。

思考時間軸thought_events

追加式保存問答、選擇、心得、留言與系統事件。

研究架構research_plans

系統初版、目前版本與修訂版號。

教師建議research_plan_suggestions

修改草稿、理由、狀態及學生決定時間。

子題與實驗experiment_records

以 subtopic_id 分組問題、做法、結果、附件與 AI 回饋。

AI 用量ai_usage

限制每日動態請求並保留模型與 request ID。

治理資料teacher_profiles / administrators / app_settings

教師核准狀態、管理者 session 與全站登入設定。

關聯刪除以資料庫外鍵 cascade 為主；清除單一研究時，該研究的事件、計畫、建議與實驗紀錄一併移除。

權限與安全邊界

瀏覽器可以持有

Supabase URL、公開 anon key、教師 JWT、學生不透明 session token，以及本機介面狀態。公開 anon key 不是管理權限。

永遠留在伺服器

SUPABASE_SERVICE_ROLE_KEY、OPENAI_API_KEY、CRON_SECRET、學生密碼雜湊與管理者密碼雜湊，不寫入 GitHub Pages。

學生存取

PIN／密碼只存 PBKDF2 雜湊；session token 也以雜湊比對。每個請求再次確認學生與 research_id 的擁有關係。

教師與管理者存取

Google 登入不等於教師授權；teacher_profiles 必須為有效狀態。管理者使用獨立 API 與 session，不共用教師權限。

資料生命週期

期限以學生資料為單位，由後端強制執行；前端顯示不能取代資料庫與排程限制。

第 0–365 天｜可編輯學生持續研究；教師查看、回饋與匯出。
第 366–395 天唯讀，供教師匯出。
第 395 天｜排程永久刪除學生、研究、事件、檔案、session 與 AI 用量
